# Developing Keycandle

How to build the firmware and the app, how the project is laid out, and how releases are made. For using the
keyboard, see the [user guide](USER_GUIDE.md).

## Layout

```
keyboard/rk71_rgb/  the QMK keyboard (copied into qmk_firmware/ at build time)
app/                the Keycandle app: Rust + GPUI (gpui-component)
via/                VIA definition, generated
docs/               user guide, Bluetooth notes, this file, README media
site/               the website (GitHub Pages)
stock/              original firmware, recovery guide, stock internals and key map
tools/              build.sh, flash_rk71.sh, stock_enter_isp.py, gen_rk71.py, udev rule for Linux
archive/            an earlier failed attempt, kept for history only
```

### Firmware (`keyboard/rk71_rgb/`)

| File | What it does |
|---|---|
| `rk71_rgb.c` | Modes, Bluetooth keys, status lights, battery, the VIA menu (custom values), macros playback |
| `rk71_defaults.h` | Every default: side-light balance, colours, times |
| `rk71_bt.c` | SPI driver for the Bluetooth module ([protocol](BLUETOOTH.md)) |
| `rk71_btcfg.c` | Settings over Bluetooth: decodes lock-light messages, reports values back ([how](BLUETOOTH.md#settings-over-bluetooth)) |
| `rk71_side.c` | Side lights and cable detection |
| `rk71_sleep.c`, `rk71_keyled.c` | Deep sleep and wake-up; dimming on battery |
| `sn32f2xx.c` | Key LED driver (replaces SonixQMK's: a short row switch, so keys refresh at ~1,430 Hz) |
| `nvm_*.c` | QMK's storage, copied; only macros differ: they live in their own 2 KB of flash (`NVM_DRIVER = custom`) |
| `keymaps/via` | The keymap (5 layers) |

`keyboard.json` and `via/rk71_rgb_via.json` are generated by `tools/gen_rk71.py`. Edit the generator, not the
outputs.

The chip has 64 KB of flash and 8 KB of RAM, and RAM is nearly full: a few bytes of new statics can stop the
build linking. `tools/build.sh` also fails if the image grows past 60 KB, where the macros start.

VIA values on channel 0 are numbered in the `ID_…` enum of `rk71_rgb.c`. The app relies on those numbers. Its tests
read that enum and fail if the app and firmware disagree.

### App (`app/`)

| Path | What it does |
|---|---|
| `src/keyboard/` | The keyboard profile: USB IDs, value numbers, matrix, Fn shortcuts, Bluetooth slots. `rk71/` is the RK71's, with its settings catalogue and key layout. |
| `src/device.rs` | VIA over USB (hidapi) |
| `src/btlink.rs` | Settings over Bluetooth: the lock-light sender and the media-code listener |
| `src/isp.rs`, `src/updater.rs` | The SN32 bootloader and installing firmware |
| `src/releases.rs` | GitHub releases and update checks |
| `src/macros.rs` | Macro bytes as VIA stores them |
| `src/ui/` | The window: one file per page, plus `model.rs` (the keyboard's state) and `app.rs` |
| `locales/` | English, Spanish, Portuguese. Every key in `en.yml` must exist in the others (a test checks). |

## Building the firmware

```
git clone https://github.com/SonixQMK/qmk_firmware.git qmk_firmware
git -C qmk_firmware checkout c9f3803f && git -C qmk_firmware submodule update --init --recursive
bash tools/build.sh                # output: build/rk71_rgb_via.bin
```

Needed on PATH:
* `arm-none-eabi-gcc`: Arm GNU Toolchain **12.2.mpacbti-rel1**, which releases are built with. Other versions
  work too but give a slightly different image.
* `make`.
* The qmk CLI: `pip install qmk` or `uv tool install qmk`.

* **Linux / macOS:** install the toolchain from [Arm](https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads)
  or your package manager. `.github/workflows/build.yml` shows a full Ubuntu setup.
* **Windows:** `winget install Arm.ArmGnuToolchain`, and MSYS2 `make` 4.4 copied to `tools/make.exe` (the
  ezwinports make breaks QMK's quoting). `build.sh` adds these to PATH by itself. Use `qmk compile` (as `build.sh`
  does), not `make kb:km`: the `make` command line is too long for Windows.

`bash tools/build.sh default` builds the plain QMK keymap instead.

## Building the app

```
cd app
cargo run --release              # the app
cargo test --release             # tests (they also read keyboard/ and via/)
```

* **Linux** needs `libudev-dev` and GPUI's usual libraries; see `.github/workflows/app.yml`.
* **macOS:** the release bundle is assembled and ad-hoc signed by the same workflow.

Useful command-line options (`keycandle --…`):

| Option | Does |
|---|---|
| `--probe` | Connect over USB and print the firmware version, key lighting and LED timings |
| `--get <ch> <id> <len>`, `--set <ch> <id> <bytes…>` | Read or write a VIA value |
| `--install <file.bin>` | Install firmware, putting the settings back afterwards |
| `--bt-set <ch> <id> <byte>` | Send one value over Bluetooth and wait for the confirmation |
| `--bt-listen [seconds] [cached]` | Ask the keyboard for its values over Bluetooth and print what arrives, with timings. With `cached`, ask as the app does (with the checksum of the remembered values) |
| `--macros`, `--macros set <n> "text"`, `--macros key <n> J`, `--macros play <n>` | List, write, assign and play macros |
| `--page <name>` | Open on a page (overview, lighting, keys, macros, power, firmware, settings) |

**Preview mode** shows the pages without a keyboard, from the values last seen. Use it for screenshots and design
work.

| `KEYCANDLE_PREVIEW=` | Shows |
|---|---|
| `1` | The pages as if connected, with sample macros |
| `updates` | An older version installed, so the update notices show |
| `charging` | The battery card charging |
| `checking` | The battery card while it checks |

## Workflow

* `main` is always the latest working release.
* Work happens on short-lived branches (`feature/macros`, `fix/caps-blink`, …), merged into `main` once tested on
  the keyboard.
* Every push builds the firmware and the app on GitHub Actions. Open a run under **Actions** and download them
  from **Artifacts** to try unreleased changes.
* If an old release ever needs a fix, branch `release/1.0.x` from its tag only then.

## Releasing

1. Add the version's row to [CHANGELOG.md](../CHANGELOG.md). It becomes the release notes, so it may not contain
   `|`.
2. Set the version in `app/Cargo.toml` and `VIA_FIRMWARE_VERSION` in `keyboard/rk71_rgb/config.h`
   (`0x00MMmmpp`).
3. Merge to `main` and push a tag:

   ```
   git tag v1.0.1 && git push origin v1.0.1
   ```

   `build.yml` builds the firmware and publishes the release. `app.yml` adds the Windows, macOS and Linux apps.
   Tags ending in `b` are betas: titled so, and the older betas are marked pre-releases.

The website (`site/`) deploys to GitHub Pages from `main` through `pages.yml`.

## Hardware and USB IDs

| Name | What it is |
|---|---|
| SN32F248BF | The chip on the board (marking). |
| SN32F240B | Its family, as in Sonix's datasheet and SonixQMK (`MCU = SN32F240B`). Same chip. |
| SN32F24xB | SonixFlasher's name for that family. Same chip. |
| `603-836/RGB-BT-HFD REV:01` | The PCB. HFD is the board maker; other Royal Kludge boards share the design. |

| USB ID | Who uses it |
|---|---|
| `0C45:8071` | **Keycandle firmware** (wired). VIA and the app talk to it. |
| `05AC:024F` | **The original firmware** (an Apple keyboard's ID), and the Bluetooth module's ID when paired. |
| `0C45:7040` | The chip's ROM bootloader (flash mode), entered with Fn + Pause or the BOOT pad. |
| `05AC:0256`, `0C45:8006` | Other original-firmware variants the vendor updater also accepts; not this board. |

From the original firmware, the vendor command puts the chip in its bootloader **without** a new USB device: it
keeps answering as `05AC:024F` (tested on the board). Fn + Pause and the BOOT pad give `0C45:7040`.

Hardware findings: [BLUETOOTH.md](BLUETOOTH.md) (module protocol), [stock/FIRMWARE_NOTES.md](../stock/FIRMWARE_NOTES.md)
(stock key map, ISP entry). The `diag` keymap toggles and shows unknown pins, which helps when mapping hardware.
VIA values 50 and 51 (read-only) report the key LEDs' measured refresh and row-switch time; `--probe` prints them.
